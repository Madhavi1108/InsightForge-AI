# Chrome E2E Audit

## 1. Scope & method

A prompt requesting a full 73-section Playwright/Chromium E2E suite (real pipeline, all pages, security, accessibility, performance, Power BI, email, recovery) was scoped down, with the user's explicit approval, to **core + representative** coverage: the real end-to-end pipeline run, all 14 Streamlit pages, real NL-to-SQL security behavior, a documented prompt-injection probe, accessibility on the primary pages, report-download validity, two cheap resilience checks (duplicate-click, refresh-mid-pipeline), responsive testing at three resolutions, and an anti-hardcoding data-variation check. This repo had zero JS/Playwright tooling beforehand - the suite (`package.json`, `playwright.config.ts`, `e2e/`) was scaffolded from scratch.

Every test runs against the **real, installed Google Chrome** (`channel: 'chrome'`, confirmed launch version 153.0.8010.48), not Playwright's bundled Chromium, with `headless: false` so the browser window is visible during execution, per explicit requirement.

## 2. Environment as actually run

- Docker Desktop started, `insightforge-postgres` container brought up and healthy via `docker compose -f config/docker-compose.postgres.yml up -d`.
- Schema applied via `python scripts/apply_schema.py` (idempotent, `CREATE ... IF NOT EXISTS`).
- Streamlit launched by `e2e/global-setup.ts` (`streamlit run streamlit_app/Overview.py --server.port=8501 --server.headless=true`), health-polled via `/_stcore/health`.
- `.env`'s `GEMINI_API_KEY` is unset, so `src/config.py`'s `LlmSettings.is_configured()` is `False` and the AI Analyst runs its deterministic **template** engine throughout - the run is repeatable, not dependent on a live LLM call.
- Node v22.14.0, `@playwright/test` 1.63.0 (installed; `package.json` pins `^1.48.0`), Chromium 1243 also present but **not used** for test execution (`channel: 'chrome'` forces real Chrome).

## 3. Findings per spec (final stable run)

**41 of 41 executed tests passed, 0 skipped, 0 flaky**, confirmed across multiple consecutive full runs after the fixes below (12 spec files total: the original 10 plus `responsive.spec.ts` and `data-change.spec.ts`, added in a later pass of this same session). See `docs/CHROME_E2E_TEST_REPORT.md` and root-level `TEST_REPORT.md`/`FINAL_ACCEPTANCE_MATRIX.md` for the full pass/fail table and timing.

Defects found and fixed during this pass (not hidden, all corrected in the suite/helpers, none in application code except where noted):
- **`pg.Pool` had no `'error'` listener**: `db-unavailable.spec.ts` stops the real Postgres container, which kills idle pooled connections; node-postgres's default behavior on an unhandled `'error'` event is to crash the whole Node process. Fixed in `e2e/helpers/db.ts` with a no-op `pool.on('error', ...)` handler (a documented node-postgres pattern, not a workaround specific to this bug).
- **`st.dataframe` renders as a canvas-based `glide-data-grid`**: cell text exists in the DOM for accessibility but is CSS-hidden (pixels are painted on `<canvas>`) - `toBeVisible()` assertions on grid cell text must be `toBeAttached()` instead.
- **BaseWeb radio inputs are visually hidden**: Streamlit's `st.radio` renders a real `<input type="radio">` with `role="radio"`, but it's styled invisible behind a custom control - the visible label text (`getByText('Run one file', { exact: true }).click()`) is the real, reliable click target, not the role-based locator.
- **The "File" selectbox is virtualized**: with 250+ files in `data/incoming/`, `st.selectbox`'s dropdown only renders a subset of options; typing to filter (`.fill(name)`) before selecting is required.
- **Streamlit `st.text_input` needs an explicit commit before the triggering button click**: `.fill()` alone doesn't reliably commit the value to Streamlit's session state before a same-tick button click causes a rerun; `.press('Tab')` after `.fill()` fixes this (confirmed via a live diagnostic - without it, `Ask`/`Run query` fire with an empty question).
- **Direct `page.goto()` to a Streamlit subpage misroutes `_stcore/health`/`_stcore/host-config`**: Streamlit's frontend issues these as relative fetches; deep-linking (rather than clicking sidebar nav like a real user) resolves them against the current path, producing benign 404s that are a test-harness navigation artifact, not an app defect. Allow-listed in `e2e/helpers/consoleTracker.ts` with this exact explanation.
- **`pg` returns `BIGINT`/`BIGSERIAL` columns as strings**: `run_id` comparisons (`toBeGreaterThan`, etc.) failed with a type error. Fixed with a global `pg.types.setTypeParser(20, Number)` in `e2e/helpers/db.ts` (safe - every ID in this schema is well within `Number.MAX_SAFE_INTEGER`).
- **Reports and Data Quality pages only list the most recent N runs** (`streamlit_app/pages/12_Reports.py`'s `LIMIT 20`, `pages/2_Data_Quality.py`'s `LIMIT 50`): as this suite's own repeated runs accumulate `SKIPPED_DUPLICATE` rows for the killer file, an older run's row legitimately scrolls off both lists over the course of a long test session. This is correct product pagination, not a bug - `full-pipeline.spec.ts` was changed to validate the original run's report file and DQ dimension scores directly against the database rather than depend on that row still being selectable in either page's dropdown/list (each page's own UI/gating behavior for *currently listed* rows is separately covered by `pages.spec.ts`, `reports.spec.ts`).
- **Stray Chrome processes across repeated headed runs**: real (non-headless) Chrome instances weren't always cleaned up between manual diagnostic runs and full-suite invocations during development. Observed twice: (1) resource contention causing a `page.goto: Target page, context or browser has been closed` failure, and (2) a more severe case where 18 accumulated `chrome.exe` processes caused `browserType.launch` to time out at 180s and a test's browser-context setup to hang for ~29 minutes before Playwright's own test-level timeout finally killed it. Both resolved by killing stray `chrome.exe` processes before the run; this is a real, recurring environment characteristic of running headed real-Chrome sessions repeatedly on this host, not an application defect - anyone re-running this suite across many iterations in one session should periodically check `tasklist | grep chrome` and clear stragglers.
- **`db-unavailable.spec.ts`'s 30s assertion timeout was too tight**: `src/database.py`'s `Database.ping()` → `scalar()` retries transient connection failures up to `DB_MAX_RETRIES=3` times with exponential backoff, each attempt capable of taking up to `DB_CONNECT_TIMEOUT=10s` before giving up - a deliberate, real resilience feature of the application, not a bug. Worst-case total can approach or exceed 30s. Fixed by raising the test's timeout to 60s to comfortably exceed the app's own real retry budget rather than fighting it.
- **Streamlit's dev server has a real concurrency ceiling**: running the `parallel` project's specs (`data-change.spec.ts`, `reports.spec.ts`, `responsive.spec.ts`, etc.) with unrestricted default worker parallelism reproducibly caused 3 specific tests to see genuinely blank/unresponsive pages (`h1` never rendering within 20s) when their sessions landed concurrently with several others against the single `streamlit run` process - confirmed reproducible across two separate full runs with the same 3 tests failing both times, and confirmed resolved (two clean 41/41 runs) after capping the `parallel` project to `workers: 2` in `playwright.config.ts`. This is a real characteristic of Streamlit's single-process dev server under concurrent browser-session load, not a flaky test or an application bug reachable by a single real user.
- **Streamlit's opt-out telemetry fetch**: `Failed to fetch metrics config: TimeoutError` / `Undefined metrics config - deactivating metrics tracking` appeared as console errors from Streamlit's own remote-metrics-config request timing out - unrelated to InsightForge's code, allow-listed in `e2e/helpers/consoleTracker.ts` alongside the other Streamlit-internal patterns.

## 4. Security findings (NL-to-SQL)

**Real, important limitation discovered**: `src/nl_to_sql.py`'s own module docstring states "no template fallback" - `generate_sql()` requires a configured LLM to translate a question into SQL *before* `validate_sql()` (the actual injection defense: banned-keyword regex, table whitelist, single-statement rule, row limit) ever runs. With no `GEMINI_API_KEY` configured in this environment (deliberately, for AI Analyst determinism), **every** NL-to-SQL question - malicious or benign - short-circuits at `ask()`'s first stage and returns `engine="unavailable"` before validation logic executes.

This means `security.spec.ts` cannot exercise `validate_sql()`'s actual blocking behavior through the browser in this environment. What it does verify for real: the app never crashes and never fabricates a SQL statement or result rows for either a `DROP TABLE` attempt or a benign question - both correctly show the honest "AI query generation is unavailable" message, with no code block rendered.

`validate_sql()`'s blocking logic itself (`BANNED_KEYWORDS`, `TABLE_WHITELIST`, single-statement enforcement) is already directly, thoroughly unit-tested in `tests/test_phase29_nl_to_sql.py` (`test_validate_sql_blocks_banned_or_multi_statement`, `test_validate_sql_blocks_multiple_statements`, `test_validate_sql_blocks_non_select_start`, `test_validate_sql_blocks_non_whitelisted_table`, `test_ask_blocks_unsafe_generated_sql`) - that suite is the authoritative coverage for this security boundary; a real end-to-end browser verification of it would require a configured Gemini API key, which was not available in this session.

## 5. Prompt-injection findings

Documented, not guaranteed. `src/ai_analyst.py`'s only defense against a misbehaving LLM response is `_is_grounded()`, which checks that every *numeric* literal in the response matches a number already present in verified evidence - non-numeric text is unconstrained. With no LLM configured, every response in this run was the deterministic template path, so the three adversarial questions in `prompt-injection.spec.ts` ("ignore previous instructions...", "reveal the database password...", "repeat ANOMALY 50 times...") all correctly returned the same honest "outside the standard business questions" template response - no credential-shaped text appeared, and no fabricated content was produced. This is real evidence for the template path specifically, not a verified guarantee against a configured LLM being manipulated; the actual rendered response for each question is attached as a test artifact.

## 6. Accessibility findings (axe, wcag2a/wcag2aa)

Two categories of real findings, both explained and neither silently hidden:
- **Streamlit's own framework chrome** (`[data-testid="stHeader"]` - MainMenu, Deploy button, toolbar; `[data-testid="stSidebarCollapsedControl"]`; `[data-testid="stSidebar"]`): `aria-allowed-attr` (disallowed `aria-expanded` on a `<span>`/`<section>`) and `button-name` (unlabeled hamburger/collapse-toggle buttons) - both critical, both in `streamlit` package markup, not `streamlit_app/` code. Excluded from the hard-fail scan (`e2e/helpers/a11y.ts`) with the finding documented here rather than fixed (not fixable within this project's own code) or silently dropped. (Initial exclusion attempt used `#MainMenu` directly and missed a sibling button outside it, plus passed multiple selectors to a single `AxeBuilder.exclude()` call - which axe-playwright treats as one nested-frame selector chain, not independent excludes - both corrected during this pass.)
- **`color-contrast`** (serious, WCAG AA): Streamlit's default `st.caption()` text color (`#83858c` on white, measured ratio 3.68 vs the 4.5:1 minimum) appears on nearly every page via captions (e.g. Overview's new "Data freshness" line). This is a Streamlit theme default used throughout the app, not a color choice made in `streamlit_app/` code. Recorded per-page as a test artifact (`axe-color-contrast-findings`) rather than hard-failing the suite, since fixing it means overriding Streamlit's theme CSS repo-wide - a deliberate styling decision beyond this E2E task's scope of testing the app as built.
- No other serious/critical violations were found on Overview, Pipeline, Anomalies, or AI Analyst after excluding the above two categories.

## 6a. Anti-hardcoding data-variation finding

`data-change.spec.ts` originally attempted to prove the dashboard isn't showing frozen/hardcoded numbers by ingesting a genuinely new, never-seen future day through the real Pipeline UI. **Real finding**: `config/data_contract.yaml`'s `Order_Date` field rule enforces a hard upper bound of `2026-09-09` - the project's fixed "narrative present." Confirmed via two real, independent attempts (submitting `data/raw/sales_2027_06_01.csv`, then a freshly-generated `sales_2026_09_10.csv` produced by the project's own `scripts/generate_dataset.py::generate_demo_day()`): both were correctly rejected end-to-end, `rows_valid=0`, DQ gate `FAILED` at score 85.71, with `rejected_records.rejection_reason = "Order_Date=<date> is after 2026-09-09"` for every row. This is the platform's own correct validation working as designed, not a bug - there is no way to ingest a post-2026-09-09 day without violating that contract, so the test was changed to the honest substitute it uses now: verifying real day-to-day variation in `daily_kpis` across already-ingested dates, plus confirming the Overview page's revenue tile matches the database's value for the latest date exactly (proving the UI reads live data, not a cached constant).

## 6b. Responsive testing

`responsive.spec.ts` covers 1366×768, 1536×864, and 1280×720 on Overview, Pipeline, and Anomalies (9 checks total): no horizontal page overflow (tolerance ≤5px for scrollbar/box-model rounding) and the sidebar navigation or its collapse toggle remains reachable. All 9 pass at all three resolutions.

## 7. Out of scope

- **Power BI**: no `.pbix`/embed target exists by design (`dashboard/*.dax`/`*.pq` are manually-pasted text assets; `docs/powerbi-data-model.md` explains why no `.pbix` is ever generated). Not browser-testable; not attempted.
- **Live email delivery**: no SMTP catcher was stood up (user decision, to avoid adding new infrastructure). Only the documented graceful no-op path is real: `src/alerts.py`'s `send_alert_email()` returns `False` and logs instead of sending when `SMTP_HOST` is unconfigured (`docs/alerts.md` §5) - the Alerts page (covered in `pages.spec.ts`) never calls `dispatch_alerts()`/`send_alert_email()` itself, by design (`streamlit_app/pages/13_Alerts.py`'s own doc comment).
- **Full 73-section literal checklist**: this suite implements the 10 user-approved core+representative items plus two cheap extras (duplicate-click prevention, refresh-mid-pipeline). Explicitly excluded: exhaustive duplicate-button-click race matrices across every button, a full performance-benchmarking suite, and exhaustive filter/pagination permutation testing beyond the representative real-vs-empty-state check in `pages.spec.ts`.
